# UX/UI review of the desktop app

**Date:** 2026-11-19 · **Build:** production build of `apps/desktop` at commit `4185eb6c` (version 0.2.0, Electron 45.2.3, Chromium 156), run unpackaged · **OS:** Windows 11 Pro 10.0.26300 · **Status:** findings only; no source was changed and no issues were filed.

Commissioned by `docs/testing/ux-ui-review-prompt.md`. Evidence labels: **Observed** (exercised or measured in the running app), **Source** (read in the code only), **Hypothesis** (plausible, not verified). Screenshots are in `2026-11-19-ux-ui-review-screenshots/`.

## 1. Executive summary

Webforge at this commit lets a first-time user get from the start screen to an exported, clean, phone-ready site without help. Every task in the matrix was completed except a real publish, which was not attempted. The app has moved a long way since the 14 November audit: most of that audit's top ten are fixed (section 6.3).

What remains is less about density and more about **the last step of each flow**: the point where the app has the answer and doesn't show it well.

**Strongest aspects to keep**

- **The quick start.** Four optional steps, friendly validation, and a site that opens as the user's own in about 5 s.
- **Undo as the safety net.** Deleting a section shows "Deleted FAQ · Undo" instead of asking; the Undo tooltip names the step ("Undo Changed Hero delay (Ctrl+Z)"); restoring a version saves the current state first and is itself undoable.
- **The title bar.** Preview, Export and Publish are labelled, Publish is the filled button, and the Site Check count ("15 to fix · 14 tips") is always visible.
- **Publish's first question** ("Where is your website hosted?") and a host form that validates before testing and arrives with the web address filled in.
- **The generated site.** No horizontal overflow, no external requests, no console errors, 14 px minimum text and a 40 × 40 px menu button at 390 px wide.

**Three highest-impact opportunities**

1. **Make Site Check readable (F1, F2, F3).** Its count is the app's main prompt to act, but clicking it opens a panel one line tall, findings name elements by internal ID ("LD5wURuiGOJhw1YE on Home"), and passed rules are mixed in with problems.
2. **Stop asking twice for a colour change (F4).** One new brand colour takes two dialogs in a row, the second with a red button, for a change that Undo reverses.
3. **Keep the selection bar off the content (F5), and let a click on text start typing (F6).** The bar covers the heading the user just edited, and a single click followed by typing does nothing.

## 2. Method and coverage

- **Build and run.** `pnpm turbo run build --filter=@webforge/desktop`, then the built app launched with Playwright's Electron driver and its own empty `--user-data-dir`, so the tour and tips showed as for a new user. One session of under an hour.
- **Test data.** Synthetic only: "Rosa's Bakery", made with **Start a Site…** (Food and drink, Café / Restaurant, Bistro, 4 pages), `hello@rosas.example`, `https://rosas.example`. One image added (a copy of a template picture under a new name). No personal data, no real credentials, no real host.
- **Window sizes (content area, CSS px at 100%).** 1366 × 768 for the walk; 960 × 600 (the minimum, `getMinimumSize()` returned `[960, 600]`); the first launch opened at 3440 × 1392. Interface text size 125% was checked at 1366 × 768 (layout width 1093 px).
- **Appearances.** Dark (default) for the walk; Light for the editor, start screen and Theme Studio.
- **Generated site.** The preview server's site and the exported folder (opened from `file://`), each in headless Chromium at 1366 × 768 and 390 × 844 (touch), six pages each.
- **Measured by script in the page:** control sizes, text contrast against the composited background, placeholder contrast, truncation, horizontal overflow, native `title` attributes, accessible names, Tab and F6 order, focus indicators. Timings are single measurements on one machine by an expert reviewer driving the app by script; they are not user-study results.
- **Stubbed.** Native file dialogs (answered by script) and `shell.openExternal`/`openPath` (captured, so no browser opened). The "Opened in your browser" toast was seen; the browser coming to the front was not.

## 4. Prioritised findings

Effort is a rough estimate. No fix has been made.

### High

**F1 · Site Check names elements by internal ID** · Site Check · **Observed** (cause: Source)

- **Evidence.** After adding an FAQ and a Section with a Heading and Button on Home, the Placeholder text rule listed "LD5wURuiGOJhw1YE on Home", "FaqItem-17778910-5602-4ae7-8159-ca92d1990903 on Home" and five more; after the Privacy fix it listed "privacy in the shared section U8z10…" (`44-site-check-tall.png`). `apps/desktop/src/renderer/site-check/describe.ts:83-84` falls back to `place.nodeId` when the node isn't found, and `:99` to `place.on` for a shared section.
- **Reproduce.** New site › add FAQ from Sections › open Site Check › Placeholder text.
- **Impact.** The user can't tell which text to change, and the app looks broken at the moment it is asking to be trusted before publishing. Task 6c.
- **Recommendation.** Never show an ID: name the element by its kind and its text ("Question 'When are you open?' on Home"), and fall back to the kind alone. Find why the lookup misses elements added in the session.
- **Acceptance.** No finding's text matches an ID pattern, for elements added since the site opened, nested elements and shared sections. **Target:** 7 of 7 placeholder findings named in words (0 of 7 now). **Validate:** an e2e test that adds each kind of element and reads the panel.
- **Effort.** Small to medium. No product decision needed.

**F2 · Site Check opens one line tall, with passed rules mixed into the problems** · Site Check · **Observed**

- **Evidence.** Clicking "15 to fix · 14 tips" opened the bottom panel 73 px tall: the tab strip and "15 should fix · 14 tips", no rows (`41-site-check.png`). Its divider is a 1 px line with a 4 px grab area and the default arrow cursor; a drag from its exact centre did not take, one 2 px lower did. Once enlarged, green "Passed" rows outnumber problems and sit between them. The summary says "should fix" and "tips" while rows say "Worth a look:" under "SHOULD FIX".
- **Impact.** The most visible call to action in the title bar leads to a panel that appears empty. Task 6c stopped here until the divider was found.
- **Recommendation.** Open the panel at about a third of the window the first time; list problems first and fold passed rules into "Passed (n)"; give dividers an 8 px grab area and a resize cursor.
- **Acceptance.** One click on the count shows at least three finding rows at 1366 × 768 and at 960 × 600, with no passed row above the last problem. **Target:** actions to see the first finding, 2 (click and drag) → 1. **Validate:** e2e measurement of the panel's height; usability task "what does Webforge want you to fix?".
- **Effort.** Small to medium. Decision: whether passed rules stay visible by default (the 14 November audit also proposed folding them).

**F3 · A finding's link selects the element without showing it** · Site Check and canvas · **Observed** (once)

- **Evidence.** Clicking the first placeholder finding selected the Heading in Layers and the Edit panel, but the canvas stayed at the top of the page with the hero in view (`43-after-show.png`).
- **Impact.** The user is told where the problem is and still has to scroll to find it.
- **Recommendation.** Scroll the selected element into view, clear of the selection bar, whenever selection comes from outside the canvas (Site Check, Layers, Find).
- **Acceptance.** After following any finding, the element's box is inside the canvas viewport. **Validate:** e2e on a page taller than the canvas; repeat the observation, since it was seen once.
- **Effort.** Small.

**F4 · One colour change takes two dialogs, the second one red** · Theme tab · **Observed**

- **Evidence.** Typing a new Brand colour and pressing Enter opened "Save Your Own Version of 'Bistro'?" (`32-after-colour.png`), then "Change the Brand Colour? … This changes 6 pages. You can undo it afterwards." with a red **Change Colour** button (`33-state.png`). Font pairing asks "Change the Fonts?" with a red **Change Fonts** (`rgb(200, 59, 61)`; `shell/confirm-site-wide.tsx:212` uses `variant="destructive"`). Deleting a section, by contrast, asks nothing and offers Undo.
- **Impact.** Choosing a colour is exploratory: people try several. Each try costs two confirmations before the result is visible, and red signals danger for something the dialog itself says can be undone. Task 5a.
- **Recommendation.** Apply the change at once with a toast ("Brand colour changed on 6 pages · Undo"), and save the user's copy of the theme silently under the default name, renaming it later from Theme Studio. If a confirmation is kept, ask once per session and use the primary button.
- **Acceptance.** A colour or font change shows on the canvas with no dialog; Undo reverses it in one step. **Target:** 4 actions → 2 from the same start. **Validate:** e2e, and a usability task "try three different brand colours".
- **Effort.** Medium. **Product decision:** this changes the site-wide confirmation rule; the trade-off is a surprise for someone who didn't realise a theme change is site-wide, which the existing "Themes change every page" tip and the toast can cover.

**F5 · The selection bar covers page content** · Canvas · **Observed**

- **Evidence.** With the Hero selected and the page scrolled, the blue bar sat on the first line of the heading just edited (`14-image-dbl.png`); selecting the new Button put its bar over the Heading above it; in Mobile view the bar covers the site's name in the header (`38-mobile-view.png`); at 960 × 600 it covers a third of the visible page (`64-light-960.png`).
- **Impact.** The thing the user is working on is hidden by the tool for working on it.
- **Recommendation.** Place the bar outside the content: above the section when there is room, otherwise below it or docked to the canvas's top edge; never over the selected element's own text.
- **Acceptance.** For a selected element anywhere on Home at Desktop and Mobile widths, the bar's box doesn't intersect the element's text. **Validate:** e2e geometry check across scroll positions.
- **Effort.** Medium.

**F6 · Clicking text and typing does nothing** · Canvas · **Observed** · proposed change to a decision

- **Evidence.** A click on the hero heading selected the Hero; typing "X" changed nothing. A double-click, or Enter, starts editing. The tour's first card and a tip say "Press Enter, or Edit on its bar". Enter with focus in Layers does not start editing.
- **Impact.** The most common task has a silent first failure; the tip repairs it, but only for those who read it. Task 2a.
- **Recommendation.** With an element selected whose main content is text, a printable key starts editing (the shortcut sheet already has "Clear Text and Edit: Backspace"), or a second click on already-selected text places the caret.
- **Acceptance.** Click a heading, type a letter: the letter appears. **Target:** wrong turns in task 2a for first-time users, to be measured in the study (section 8). **Validate:** usability test; e2e.
- **Effort.** Medium. **Trade-off:** single-key shortcuts on a selection (such as `?`) need to stay out of the way.

**F7 · Most controls are smaller than 24 × 24 px** · Whole editor · **Observed** · WCAG 2.2 SC 2.5.8 (AA)

- **Evidence.** At 100% text size, 129 of 176 visible controls measured under 24 px in one dimension: list rows 21 px tall and touching (Add panel, Layers, Pages, Menu), Layers eye buttons 18 × 18, panel buttons 21 × 21, menu-bar items 21 px tall, Site Check links 18 px tall. Touching 21 px rows don't meet the spacing exception. Italic and Underline switches are 25 × 14. At 125% the count was 89 of 132.
- **Impact.** Mis-clicks for everyone, a barrier for people with limited dexterity.
- **Recommendation.** Raise row and icon-button height to 24 px at 100% (three more pixels per row), or make 110% the default text size.
- **Acceptance.** No control under 24 × 24 px at the default size, apart from inline links in sentences. **Validate:** the measurement script as a test on the main editor states.
- **Effort.** Medium (visual regression screenshots change). **Trade-off:** fewer rows per panel.

## 5. Consistency and accessibility patterns

**Good patterns to reuse**

- **Undo instead of confirm** (delete a section, restore a version) with a toast naming what happened. F4 and F17 are the places it isn't used yet.
- **Disabled with a reason**: the Edit menu shows "Select an element first." beside Duplicate. Use it for every disabled control.
- **Validation that names the fix**: "Use an email address such as hello@example.com."; "Enter your host's address, such as ftp.example.com."
- **A question before a form**: Publish's "Where is your website hosted?", with "I don't have a host yet" leading to the right help page.
- **Tooltips with name and shortcut** on the title bar and the selection bar.

**Recurring problems**

- **The app knows, but doesn't show**: Site Check's panel height (F2), a finding's element off-screen (F3), the export report against Site Check (F8), a fix with no message (F17), the error under the sidebar (F18).
- **Internal values reaching the user**: element IDs (F1), hex and px (F15), contrast ratios, file names in dialogs ("File name: new-page.html").
- **Site-wide changes treated as dangerous**, single destructive ones as safe (F4).

**Verified failures (WCAG 2.2 AA)**

| Criterion                   | Where                                              | Evidence                                    |
| --------------------------- | -------------------------------------------------- | ------------------------------------------- |
| 2.5.8 Target Size (Minimum) | List rows, Layers buttons, panel buttons, menu bar | F7: 129 of 176 controls under 24 px at 100% |
| 2.4.7 Focus Visible         | Slider                                             | F12                                         |
| 2.4.6 Headings and Labels   | Site Check "Fix" buttons                           | F17                                         |

**Verified passes on what was measured**

- Text contrast: no failures among visible text on the editor (Dark and Light), start screen (Light) and Theme Studio (Light). Placeholders 6.65:1 in Light.
- Every visible control on those screens has an accessible name.
- F6 moves between canvas, bottom panel, right panel, title bar and left panel; Tab order follows the screen; focus rings were visible on every stop checked except the slider and the 1 px dividers.
- Text size 125% at 1366 × 768: no clipping or horizontal scrolling (layout 1093 px wide; right panel 793–1093 px).
- Generated site at 390 px: no overflow, no control under 24 px, menu button 40 × 40 px with the name "Menu".

**Needs manual assistive-technology testing**

- Screen-reader announcement of selection, of toasts ("Deleted FAQ"), of the save status and of Site Check results.
- Editing on the canvas by keyboard alone from a cold start (Enter worked after a mouse click; arrow-key selection did not move in one attempt and was not pursued).
- Windows high contrast and forced colours; the generated site with a screen reader; the mobile menu's state (it is a `summary`, so no `aria-expanded` was present to read).
- Dark-appearance contrast of dialogs, the quick start and the Help window.

## 7. Human validation plan

**This is a plan, not research.** Nothing below has been run; the targets are proposals to confirm or revise.

- **Who.** Five small-business owners or people who would build a site for one, who have not used Webforge and have not built a website with a developer tool. One at a time, about 60 minutes, on a 13–14 inch laptop with the installed build and a fresh profile. This extends `docs/testing/usability-5.4a.md` (three people, one long task) with shorter measured tasks; the two can share sessions.
- **Method.** Think aloud; the facilitator stays silent unless the person is stuck for 3 minutes, then gives the smallest hint and records it. Record time per task from reading it to saying "done", wrong turns (a click that doesn't move towards the goal), hints and help opened. A test host as in 5.4a for the publish task.
